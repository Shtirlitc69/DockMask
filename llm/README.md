# LLM layer

Техническая документация слоя `llm`. Модуль изолирует провайдеры моделей от pipeline: `core` знает только контракт `BaseLLMClient`, а создание клиента, хранение ключа и настройка HTTP выполняются уровнем `app`.

## Назначение

LLM используется для поиска ФИО, организаций, адресов и сумм в контексте, а также определения роли стороны документа. Регулярные выражения ответственны за структурированные реквизиты: ИНН, КПП, ОГРН, телефон, e-mail, счёт, БИК и номер договора.

Это уменьшает зависимость результата от модели и позволяет менять GigaChat на другой совместимый провайдер без изменений бизнес-логики.

## Контракт `BaseLLMClient`

| Метод | Результат и обязательства |
| --- | --- |
| `find_entities(text, types)` | Возвращает точные `EntitySpan` только для запрошенных типов. Координаты вычисляются по исходному тексту, а не принимаются от модели. |
| `classify_party(context_snippet, candidate_name)` | Возвращает `supplier`, `buyer` или `None`, если роль неизвестна. |
| `list_llm_models()` | Приводит список моделей провайдера к `LLMModelInfo`. |
| `validate_llm_connection()` | Выполняет синтетическую проверку подключения и возвращает безопасный код результата. |

`get_llm_client(config, http_client)` — единственная фабрика создания адаптеров. Клиент получает уже разрешённые `LLMClientConfig` и долгоживущий `httpx.AsyncClient`; не читает окружение, файлы конфигурации или Windows Credential Manager и не закрывает переданный HTTP-клиент.

## Провайдеры

| Идентификатор | Назначение |
| --- | --- |
| `mock` | Детерминированный режим без сети для тестов и безопасной демонстрации. |
| `gigachat` | Основной облачный AI-провайдер для кейса. OAuth, scope и TLS настраивает приложение. |
| `openai`, `anthropic` | Облачные провайдеры с ключом API. |
| `openai_compatible` | Совместимый API с указанным пользователем URL. |
| `ollama`, `vllm` | Локальные или самостоятельно развёрнутые модели. |

Обычный HTTP разрешён только для loopback-адресов. Все остальные пользовательские URL должны использовать HTTPS.

## Формат ответа модели

Адаптеры ожидают компактный JSON. Допускается JSON в Markdown-блоке.

```json
{"entities":[{"type":"organization","text":"ООО Тест"}]}
```

```json
{"role":"supplier"}
```

Лишний текст, повреждённый JSON или отсутствие нужных полей приводят к `LLMResponseError`. Неизвестный, незапрошенный тип или значение, отсутствующее в исходной строке, игнорируется. Не включайте значение такого ответа в логи.

## Контекст, конфиденциальность и ошибки

В модель передаются отдельные `TextBlock`, а не файл целиком. Лимит контекста определяется провайдером; большие блоки дробит application layer до обращения к адаптеру.

При GigaChat, OpenAI или Anthropic анализируемый текстовый блок покидает компьютер. Ключи хранятся только backend в Windows Credential Manager, не отдаются через API и не должны попадать в логи. Для воспроизводимых тестов используйте `MockLLMClient` и только синтетический текст.

Текущая версия промптов определена в `PROMPT_VERSION`; шаблоны находятся в [`prompts.py`](prompts.py).

## Как добавить провайдера

1. Реализуйте `BaseLLMClient` в отдельном модуле.
2. Добавьте идентификатор в `ProviderId`, описание в `PROVIDER_SPECS` и ветку фабрики в `factory.py`.
3. Нормализуйте список моделей в `LLMModelInfo` и возвращайте только безопасные ошибки подключения.
4. Добавьте unit-тесты с синтетическими ответами, включая повреждённый JSON, незапрошенные типы и несовпадающий текст.
5. Не переносите в адаптеры доступ к секретам, файловой системе или логике pipeline.
