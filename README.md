# TriemaDeid

TriemaDeid - локальное Windows-приложение для обезличивания конфиденциальных данных в тендерных документах. Приложение принимает PDF, DOCX и XLSX, находит выбранные типы сущностей, заменяет их маскирующими маркерами и возвращает файл в исходном формате с визуальной подсветкой изменений. Вместе с результатом формируются JSON- и XLSX-отчёты для ручной проверки.

Этот README фиксирует контракт и устройство целевого MVP. Реализация ведётся поэтапно: первый сквозной формат - DOCX, затем подключаются XLSX и PDF. OCR сканированных PDF является отдельным расширением после базового MVP.

## Возможности целевого MVP

- Приём PDF, DOCX и XLSX и выбор типов данных для обезличивания.
- Извлечение текста и структуры документа, включая таблицы.
- Поиск сущностей правилами и через LLM с объединением и устранением пересечений.
- Определение поставщика и покупателя по контексту документа.
- Уточняющие вопросы, когда роль стороны определить нельзя.
- Замена сущностей маркерами с сохранением исходного формата и подсветкой изменений.
- JSON- и XLSX-отчёты со всеми применёнными заменами.
- Локальная очередь с одним фоновым worker.
- Смена облачной или локальной LLM без изменения доменной логики.

## Обработка документа

1. Пользователь загружает файл и выбирает типы сущностей.
2. Экстрактор преобразует документ в текстовые блоки с координатами внутри исходной структуры.
3. Rule-based и LLM-детекторы находят сущности; пересечения удаляются, а одинаковым значениям назначаются стабильные маски.
4. Для организаций и физических лиц определяется роль `supplier`, `buyer` или `unknown`.
5. Если обязательная роль не определена, pipeline возвращает вопросы и состояние `needs_clarification`, не создавая конечный документ.
6. После получения ответов задача снова ставится в очередь и продолжает обработку с сохранёнными кандидатами, не вызывая LLM повторно.
7. Redactor применяет замены, подсвечивает маски и создаёт новый файл, не изменяя исходник.
8. Сервис формирует JSON-отчёт и публикует результат только после полного успеха.

Это последовательный расширяемый pipeline с адаптерами, а не распределённая мультиагентная система.

## Архитектура

```text
React 19 + TypeScript + Vite + Tailwind CSS v4
                  │ относительный /api
                  ▼
FastAPI на 127.0.0.1:<свободный порт>
                  │
          asyncio.Queue + 1 worker
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     core/       llm/     storage/
    pipeline    адаптеры    SQLite
```

- **Frontend.** Исходники находятся в `frontend/`, production-сборка - в `frontend/dist/`. Русские подписи и пользовательские тексты формируются только во frontend.
- **FastAPI.** `app/` содержит JSON API, Pydantic-схемы, lifecycle и подключение зависимостей. Бизнес-правила в transport-слой не помещаются.
- **Доменный слой.** `core/` не импортирует FastAPI и напрямую не работает с SQLite.
- **LLM.** Все провайдеры реализуют `BaseLLMClient`; pipeline не зависит от конкретной модели.
- **Хранение.** SQLite хранит метаданные задач, а файлы размещаются в локальных каталогах, изолированных по `job_id`.
- **Desktop-оболочка.** pywebview запускает локальный FastAPI, ждёт `/api/health` и открывает фактический HTTP URL в WebView2.

Jinja2, HTMX, `app/templates`, `app/static` и `routes_ui.py` не входят в целевую архитектуру React-MVP.

Backend возвращает только стабильные машинные значения. React сопоставляет их с русскими подписями.

## HTTP API

Все production-запросы frontend выполняются по относительному пути `/api`. Идентификатор задачи - UUID.

### `POST /api/jobs`

`multipart/form-data`:

- `file` - PDF, DOCX или XLSX;
- `entity_types` - одно или несколько повторяющихся значений из справочника;
- `ocr_enabled` - `false` в базовом MVP.

Ответ содержит `job_id`, `status`, `source_filename` и `document_format`.

Сервис проверяет расширение, непустой список сущностей и максимальный размер файла. Исходное имя сохраняется только как метаданные; файл записывается под безопасным внутренним именем в каталоге задачи.

### `GET /api/jobs/{job_id}`

```json
{
  "job_id": "uuid",
  "status": "processing",
  "progress": 40,
  "questions": [],
  "total_replacements": 0,
  "error": null
}
```

### `POST /api/jobs/{job_id}/answers`

```json
{
  "answers": [
    {"question_id": "party:block:0:12", "answer": "supplier"}
  ]
}
```

Допустимые ответы на вопрос о стороне: `supplier`, `buyer`, `unknown`. После получения всех обязательных ответов задача один раз возвращается в очередь.

### `GET /api/jobs/{job_id}/document`

Выдаёт обезличенный файл только при `done`. Имя передаётся через `Content-Disposition`.

### `GET /api/jobs/{job_id}/report`

Выдаёт JSON-отчёт только при `done`. Каждая запись содержит `entity_type`, `original_value`, `replacement`, `location`, `source`, `confidence`, `party_role` и `applied`.

### `GET /api/jobs/{job_id}/report.xlsx`

Выдаёт оформленный XLSX-отчёт с закреплённой строкой заголовков, фильтром и числовым процентным полем уверенности.

### `GET /api/config` и `PUT /api/config`

`GET` возвращает публичные настройки, feature flags и `has_api_key`, но никогда не возвращает секрет. `PUT` принимает необязательный write-only `api_key`; ключ хранится в Windows Credential Manager.

`POST /api/config/validate` проверяет одноразовую или сохранённую конфигурацию без её записи. `GET /api/config/models` получает список моделей через backend; frontend не обращается к провайдерам напрямую.

### `GET /api/health`

Возвращает доступность приложения, SQLite и worker без секретов и персональных данных.

### Ошибки

- `404` - задача не найдена;
- `409` - результат ещё не готов или операция не соответствует статусу;
- `422` - неверный файл, тип сущности или ответ;
- `failed` - безопасный машинный код внутренней ошибки без traceback и содержимого документа.

## Очередь и хранение

Таблица `jobs` содержит идентификатор, статус, исходное имя, внутренние пути, запрошенные типы, вопросы, ответы, progress, число замен, ошибку и timestamps.

- Схема SQLite инициализируется идемпотентно.
- Одно соединение открывается на lifecycle приложения.
- SQL использует параметры.
- Изменения состояния выполняются транзакционно.
- Оставшиеся после перезапуска `processing` переводятся в `failed` с кодом `processing_interrupted`.
- Исходник никогда не перезаписывается.
- Частично созданные output/report не выдаются пользователю.

## Запуск и сеть

### Разработка

- Backend запускается через `uvicorn app.main:app` на `127.0.0.1:8000`.
- Vite proxy перенаправляет `/api` на development backend.
- Node.js и pnpm нужны только для разработки и сборки frontend.

### Production `.exe`

1. Python-оболочка выбирает свободный loopback-порт.
2. FastAPI запускается на `127.0.0.1:<port>` и раздаёт `frontend/dist`.
3. Оболочка ждёт успешный `/api/health`.
4. pywebview открывает `http://127.0.0.1:<port>/`.
5. При закрытии окна worker и FastAPI корректно останавливаются.

Сборка выполняется из PowerShell командой `scripts/build_windows.ps1`. Готовый файл создаётся как `output/exe/DockMask.exe`; скрипт предварительно запускает backend/frontend-проверки и останавливается, если React-сборка или встроенный сертификат отсутствуют.

Локальные данные размещаются через `platformdirs` в каталоге профиля пользователя. SQLite и задания находятся в каталоге данных DockMask, технические ротационные логи — в подпапке `logs/dockmask.log` (до трёх архивов по 2 MiB). В логи запрещено помещать текст документов, значения сущностей, промпты, ключи, OAuth-токены и тела ответов LLM. Версионируемые промпты входят в приложение как `llm/prompts.py`, а не копируются в runtime-логи.

Нельзя открывать интерфейс через `file://`, слушать `0.0.0.0` или включать CORS `*`.

### Интернет и офлайн-режим

- Первая установка pnpm-зависимостей требует интернет, если пакетов нет в локальном кеше.
- Повторная сборка возможна офлайн при наличии lockfile и кеша пакетов.
- Готовый `.exe`, FastAPI, frontend и локальная обработка документов работают без интернета.
- Интернет требуется только при использовании облачной LLM.
- С заранее установленной локальной моделью приложение работает полностью офлайн.
- Все стили, шрифты, иконки и runtime-файлы входят в `frontend/dist`; Google Fonts, CDN и внешняя аналитика запрещены.

## Тестирование целевого MVP

- Модульные тесты проверяют модели, extractors, детекторы, redactors и отчёт.
- Асинхронные тесты репозитория используют временную SQLite-базу.
- API-тесты проверяют загрузку, polling, ответы, ошибки и скачивание результата.
- DOCX E2E-fixture содержит абзац, таблицу, несколько runs и размеченный список замен.
- E2E проверяет неизменность исходника, отсутствие исходных значений в результате, подсветку масок, сохранение форматирования и согласованность отчёта.
- Vitest проверяет API-клиент и состояния frontend.
- В логах теста не должно быть исходных конфиденциальных значений.
- Контрольный прогон выполняется с `MockLLMClient`; облачная модель не вызывается.
